# frozen-probe-operating-point

Code and records for the paper *Operating-Point Failure of Frozen Guardrail Probes Under Backbone Updates*, by Yusuf
Khalid Shire and Sang-Chul Kim.

The guardrail we study is a linear probe on a language model's hidden states that flags harmful prompts, with its
threshold set once for a target false-positive rate. We keep the probe and its threshold frozen while the model
underneath is replaced by a released update or a controlled fine-tune, and measure where the operating point lands:
the false-positive and detection rates the old threshold now gives, whether ranking (AUROC) shows the change, whether
the checks a deployer would run notice it, which repairs restore the rate without new labels, and what an attacker who
controls the update can do.

What can be checked from this repository:

- **Every result number the paper prints can be found in a record here.** The paper and its supplement have 149
  sentences that print a result number. For 135 of them, `release/numbers_map.tsv` names the result records they read,
  and every one of those records is here. The other 14 print counts of our registry of predictions
  (`docs/registered_predictions.md`, here) or of our decision log (not here). The paper's generated tables and figures
  read only records that are here.
- **The six generated table and figure files can be regenerated byte for byte** (below).
- **Every SHA-256 the records state can be checked** against the files here (`release/verify_inputs.py`, below).

What cannot: a number that a record computed from the hidden-state activations cannot be recomputed here, because the
activations are not released (209 GiB); they can be regenerated with the code in `src/` and the checkpoint revisions the
records name. Many records also read other records that are not here (see "What is not here"). Each record names the
commit and SHA-256 of the code that wrote it, its parameters, and the SHA-256 of every file it read, and those hashes
also fix the bytes of the records it read that are not here.

## What is here

- `src/`: all of the Python. Splitting the datasets, extracting hidden states, fitting probes, the analyses, Phase 3's
  attackers and defences, and the five scripts that write the tables and figures. It is one flat directory because the
  modules import one another by name and the records name them by these paths. `release/modules.md` says, for each
  file, whether it runs here, and which parts of the paper read its records.
- `results/`: 284 result records: the 108 that the table and figure writers read, the records that the paper's
  sentences read, and the records of the datasets and splits.
- `manifests/splits/`, `manifests/splits_p2/`, `manifests/splits_p2_v2/`: one manifest per frozen split, with each
  item's identifier, label and source row, and the SHA-256 of the split file. No prompt text. The Phase 3 split is
  recorded in `results/phase3_capcost_wgtest_split.json`.
- `docs/registered_predictions.md`: the registry of our predictions. For each one it gives the wording, the decision-log
  entries that registered and scored it, the result files with their hashes, and the verdict.
- `docs/paper/`: three records that the paper reads and that were computed on the authors' workstation:
  `config_deltas_d471.json` and `review_20261016b_calc.json` (read by two of the writers) and `apply_d498.json` (read by
  one sentence of Section V-G); and the three scripts that produced the first two. `scripts/tally_ledger_verdicts_d449.py`
  is imported by one of those scripts, and `logs/table3_tpr_d282_20261003.sha256` is a hash list that one writer
  checks before it trusts a record.
- `release/`: files written for this release: `numbers_map.tsv`, `modules.md`, `substitutions.json` and
  `verify_inputs.py` (below).
- `requirements-tables.txt` and `requirements.txt`: pinned environments for the writers and for the experiments.
- `config/example.env`: every setting the code reads from the environment, with example values.
- `PROVENANCE.md`: the files whose bytes differ from the ones that produced the results, and why.

Every file sits at the path it had in our working repository. The code finds its inputs by those paths and the
records name them, so moving a file would mean editing code and breaking the hashes. That is also why three records sit
under `docs/paper/` and a hash list under `logs/`.

`release/numbers_map.tsv` has one row per sentence of the paper and its supplement that prints a result number, and
one row per generated table or figure file. Its columns: the LaTeX source file and line (of the submitted source); the
section; our claim IDs (the claims table of the Introduction uses them); the numbers printed; how the records were
found (a binding, written by hand by someone who read the number at its key; named in the claim's row of our claims
table; or a candidate reached through a wildcard in that row, so a superset of what was read); the records, all of
which are here; how many of the sentence's decimal numbers appear, at the printed precision, as a value in one of
those records (a weak check: a decimal can match a value by chance); and the number of probe-score arrays among the
candidates, which are not released. No sentence's record is missing.

## Reproducing the tables and figures

The writers need Python 3.12 and numpy, nothing else. From the repository root:

```sh
python3.12 -m venv .venv
. .venv/bin/activate                        # Windows: .venv\Scripts\activate
pip install -r requirements-tables.txt
mkdir -p build/tables
export GUARDRAIL_PAPER_DIR=build/tables     # Windows PowerShell: $env:GUARDRAIL_PAPER_DIR = "build/tables"
python src/config_table_d472.py
python src/pairs_table_d468.py
python src/results_tables_d504.py
python src/results_figures_d570.py
python src/supp_tables_d585.py
```

Keep this order: `supp_tables_d585.py` reads back the `tables_results.tex` that `results_tables_d504.py` writes. The
scripts read only files in this repository and write only into `GUARDRAIL_PAPER_DIR`, which is taken relative to the
root and must lie inside the repository. Left unset, it is `paper/`.

| File written | Where it appears in the paper |
|---|---|
| `tables_config.tex` | the table of configuration changes of the update pairs (`tab:config`) |
| `tables_results.tex` | the three Results tables: the headline cells (`tab:headline`), the matched-dose LoRA arms (`tab:lora`) and the estimated-rate check per Phase 1 cell (`tab:fourc`) |
| `figures_results.tex` | the figure of realised paired ratio against the estimated rate ratio (`fig:fourc-scatter`) |
| `tables_pairs.tex` | Supplement: the update pairs and their cells (`tab:pairs`) |
| `tables_supplement.tex` | Supplement: `tab:x5`, `tab:geomean`, `tab:contrast` and `tab:lastgen` |
| `figures_supplement.tex` | Supplement: paired ratio against layer (`fig:layer-sweep`) |

The figures are pgfplots code, not images, so their numbers can be read in the `.tex` files. We regenerated all six
files in a fresh environment, from this repository's files alone. Each was byte-identical to the file the manuscript
is built from.

Two tables cannot be regenerated here: the registry table in the Supplement (`tab:registry`) and the claims table in
the Introduction (`tab:claims`). Their writers read the manuscript's LaTeX source, to find the section where each claim
is stated, and our internal claims table and decision log; none of these is in this repository, and neither are the
writers. The registry that the first of them typesets is `docs/registered_predictions.md`.

## Checking the hashes

```sh
python release/verify_inputs.py
```

It needs Python 3.10 or later and nothing else, reads files only, and writes nothing. For every (file, SHA-256) that a
record here lists, and every hash that the registry cites, it prints PASS (the file is here with that hash),
SUBSTITUTED (the file is one of the 15 whose bytes we changed for publication, listed in `release/substitutions.json`;
the stated hash is the original's, which a reader cannot check from here), OTHER VERSION (a code file or document that
the record read at an earlier version; this repository ships one version of each, and the record names the commit of
our working repository that it ran at, which is not public), ABSENT (the file is not here) or FAIL. It exits 1 on any
FAIL. On this repository it reports no FAIL.

## Which code runs here

`release/modules.md` has one row per Python file. In short: the five table and figure writers and the hash check run
here. 55 files are for inspection only, because they name paths under `logs/` or `queues/`, which are not here (38 and
11 files), or import a GPU-stage library (torch, transformers, peft, datasets, huggingface_hub, safetensors or
tokenizers). The other 95 run only where their input files are; many of those inputs are hidden-state caches or
records that are not here, and each file's row counts the records here whose code block names it and that read
caches.

## Re-running the experiments

This is a far larger job than regenerating the tables. It needs the following.

- Linux and NVIDIA GPUs. The GPU stages are extraction (one forward pass per prompt, no generation), LoRA training, and
  Phase 3's attack training and capability-cost scoring. The probe fits and the analyses run on CPU. The paper's
  Method section says which cells ran on which GPU type.
- NVMe storage. Every script that fetches or loads weights calls `src/hf_env_guard.py`, which refuses to run unless
  `HF_HOME` lies on an NVMe device as `/proc/self/mounts` reports it. The Phase 2 extraction, the Phase 2 and
  Phase 3 trainers and the capability-cost harness make the same check of their own directories.
- Python 3.10 with the versions in `requirements.txt`. torch is the CUDA 12.6 build.
- The settings in `config/example.env`. A Hugging Face token for gated checkpoints and datasets goes in a file named
  `.env` at the repository root, where `src/fetch_weights.py` reads it. The guard refuses to run while a token is set
  in the environment.
- The datasets. Each comes from its owner under its owner's licence, and we redistribute none of their text.

The records come from three machines. Each record names the platform and Python version it ran under, except four
here that name none: the three under `docs/paper/`, calculations made on the authors' workstation, and
`results/paraphrase_per_item_safety.json`. Every record written on or after 2026-09-25 also names its package versions;
no earlier record does.

- A Linux host with a Tesla V100-DGXS-32GB GPU (kernel 5.14, Python 3.10.12) wrote 73 records, from 2026-09-14 to
  09-17: Phase 1's extraction and early work. None of them names its packages, so the library versions behind the
  Phase 1 activation caches, from which many of the paper's numbers derive, are not recorded.
- A Linux container (Ubuntu 22.04.5, Python 3.10.12) on a node with an NVIDIA A100-SXM4-40GB GPU wrote 1,674 records,
  from 2026-09-17 to 10-13. The 1,495 written from 2026-09-25 on name numpy 2.2.6, scipy 1.15.3, scikit-learn 1.7.2,
  torch 2.7.0+cu126 and transformers 4.56.1, the versions in `requirements.txt`; the 179 written before name none.
  `requirements.txt` also pins urllib3 and PyYAML, which no record names, at the versions installed on that node
  before its first record (the file says how they were read).
- The authors' Windows 10 workstation (Python 3.12.10) wrote 25 records; the 17 written from 2026-09-25 on name numpy
  2.5.3, scipy 1.18.1 and scikit-learn 1.9.1, and no torch. The workstation records that the paper's numbers read
  compute from other records; none of them reads the activations or resamples.

| Dataset | Used for |
|---|---|
| `nvidia/Aegis-AI-Content-Safety-Dataset-2.0` | the Phase 1 safety splits |
| `allenai/wildguardmix` | the Phase 1 and Phase 2 safety splits; its test set gives the Phase 3 split |
| `natolambert/xstest-v2-copy` | the over-refusal split (XSTest) |
| `nyu-mll/glue` (SST-2) | the non-safety control of Phase 2 |
| `yahma/alpaca-cleaned`, `Anthropic/hh-rlhf`, `PKU-Alignment/PKU-SafeRLHF` | training the controlled LoRA updates |
| `allenai/ai2_arc` (ARC-Easy) | the capability-cost measurements of Phase 3 |

The revision each split was built from is recorded: Phase 1's in `results/dataset_manifest.json` and
`results/dataset_manifest_wildguard.json`, Phase 2's in `results/phase2/dataset_manifest_p2*.json`, and Phase 3's in
its split record. To rebuild a split, run the script that its manifest's note names against that revision, then
compare the SHA-256 of the file it writes with `sha256_of_original` in the manifest. The revisions of the LoRA corpora
and of ARC are in the training and capability-cost records, and the checkpoints of each update pair, with their
revisions, are named in the configurations of the records.

We kept no total of GPU or CPU time and do not estimate one here. Each record carries the UTC time at which it was
written.

## What is not here, and why

- Dataset prompt text. The licences belong to the datasets' owners. The split manifests carry identifiers and hashes,
  so a rebuilt split can be checked against ours.
- The canary prompts as a list. One of the defences in the paper checks detection on a set of held-out labelled
  harmful prompts; in a deployment, only the deployer would hold them, and the defence works only while an attacker
  cannot know which prompts they are. In this study they are not secret: they are public-dataset prompts chosen by a
  deterministic rule. A split manifest here lists them among the 1,000 positives of one split, and the code that
  selects them, with its seeds, is in `src/`, so a reader with the public dataset can work out which they are. No
  attack in the study saw them: the attack the canary was tested against was trained and scored before the canary was
  fixed, and no attack or evaluation split contains a canary prompt. A deployer should draw its own set and keep it
  private.
- Model artefacts: the LoRA adapters of the controlled updates, the attacked models of Section V-H, and any
  checkpoint. They are too large for git, and whether to release a model update that evades the monitor is a decision
  we have not yet made. The code that trains them is in `src/`.
- Caches: the hidden-state activations and the probe scores (as arrays). The extraction code regenerates them.
- The records deeper in the chain. The records here are the ones the paper's numbers and the table and figure writers
  read, and the dataset and split records. The records those were computed from are not here: many of them name
  private paths of our compute node or name harm categories by their dataset labels, some in their file names, which
  other records cite by path, so they cannot be published unchanged without breaking the hashes that cite them. The
  hashes the records here state fix their bytes. Where they will be deposited is not yet decided: [ARCHIVE LOCATION:
  placeholder, to be filled in].
- The decision log. Each registry row cites, by D-number, the entries of our decision log that registered and scored
  the prediction. Those entries and their dates are not in this repository yet, so the order of registration and
  scoring cannot be checked from here alone.
- Our test suite, the scripts that ran jobs on our compute node, and the writers of the claims and registry tables.

## Files changed for publication

Fifteen files differ from the code and records that produced the results; `release/substitutions.json` lists each
with both SHA-256 values and its size, and `PROVENANCE.md` says what changed.

- In eight modules an output directory or the compute node's home path became a setting. Three modules check the
  SHA-256 of `src/p2auroc_d424.py`, one of the eight, before they run, and their pins now hold its new value; two of
  the three are among the eight, and the third changed in that line only. Their diffs are in `PROVENANCE.md`.
- In three records, five absolute paths each, under the compute node's home directory, became `<HOME>`. Their diffs
  are in `PROVENANCE.md`. This removes an account name from the text; because the records publish the original files'
  SHA-256, it does not make the name unrecoverable.
- In three Phase 3 records (the attack's verdicts and the two defences' records), every harm-category label became
  the neutral ID the paper uses (cat-1, cat-2, ...), and in one of them one absolute path of our compute node became
  `<REPO>`. Only those strings changed, in keys and in values: every number is unchanged and in the same place, and
  every object and list has the same number of entries. Their diffs are not published, because a diff would print the
  labels.

Every other file copied from our working repository is byte-identical to its original. The files written for this
release are listed in `PROVENANCE.md`.
