# Registered predictions ledger

Every pre-registered prediction, decision rule and registered expectation in `DECISIONS.md`, with the RESULT entry that scores it, the result file and its hash, the verdict and the key number exactly as the RESULT entry states it.

## What this file is

- A reading aid and audit table over the append-only ledger `DECISIONS.md`. It is derived; it decides nothing and re-scores nothing. A verdict here is the RESULT entry's own word (HELD, FAILED, UNDEFINED, NOT YET RUN, NOT SUPPORTED, REFUTED, INCONCLUSIVE); where an entry states a rule's outcome without such a word the row says OUTCOME ONLY and quotes the entry. No number is computed, rounded or restated here (CLAUDE.md rule 2): every number is copied from the RESULT entry, and the hash column is computed from the file on disk.
- Generated from the ledger on 2026-10-08 at commit `5cbad8a81bf78d68173e0682d9ca5dcbc1ab94aa` (branch `preds2`; the ledger then ends at D-421 and holds no D-418). First generated on 2026-10-07 at commit `dfc08cfe12e5af050eb1f219f0dcbd7c51f88832` (branch `predsdoc`, taken from `master`; the ledger then ended at D-386).
- Result-file hashes: `sha256sum <path>`, first 16 hex characters, computed on this tree. Where a RESULT entry names a hash prefix the row says `match` or **MISMATCH**. Entry-named prefixes are compared as the entry wrote them (8 to 16 hex).
- Number check against the files: for every row that names a JSON result file (or a glob) the decimal numbers in the key-number column were looked up in that file; the outcome, including the one rounding-level MISMATCH found and the numbers the files do not store, is in the section "Entry versus file" below. Rows with no file, and pooled numbers that an entry derived and the file does not store, were not re-derived.
- Storage (D-489, 2026-10-17): a pipe inside a cell is written `\|` (GitHub's table escape), so every row splits into its 8 columns on unescaped pipes only; read rows with `scripts/ledger_rows_d489.py`, never with a plain split on `|`. A row's status is the leading word of its Verdict cell (D-487 (4)).

## How to update

1. Append-only: add rows, do not edit a verdict word; if a later entry corrects a number (as D-089, D-120 and D-322 did) add the correction beside the original in the same row and name the correcting entry.
2. For a new pre-registration entry (type contains PRE-REGISTRATION, or an entry that registers predictions, expectations or decision rules before its results): add one row per label (`P-...`, `H-...`, or a short name when unlabelled), verdict `NOT YET RUN`, result `none yet`. If it registers no outcome prediction (protocol, definition, descriptive), add it to Appendix B instead.
3. For a new RESULT entry: find the pre-registration it scores (`grep -n 'D-NNN' DECISIONS.md`, and the label, e.g. `grep -n 'P-A1.3' DECISIONS.md`), then fill RESULT, file path, the first 16 hex of `sha256sum`, the verdict copied from the entry and the key number as the entry states it.
4. Check any hash the entry names against the file; write both and flag **MISMATCH** if they differ. Write both and flag **MISMATCH** also where the entry and the file disagree on a number.
5. Update the summary count and the commit named above.
6. A reviewer samples at least 20 rows against `DECISIONS.md` and the files before the document is relied on (D-385 (1)).
